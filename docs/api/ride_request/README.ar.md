# تسليم باكند طلب الرحلة — Tam | تم

**العقد:** `ride_request-v1` — **الحالة: مقترح للتنفيذ، غير منفذ أو متحقق حيًا**.
**التاريخ:** 2026-11-07. **المالك:** W1-RIDE (B).

## التدفق المطلوب

1. اختيار الانطلاق/الوجهة عبر البحث عن أماكن محاكاة، مع إمكانية إعادة الطلب من `TripPrefill` (الموقعان فقط).
2. اختيار `standard | comfort | van | motorbike` وطلب عرض سعر جديد لكل تغيير في المواقع أو الفئة.
3. عرض الأجرة والمسافة والمدة وتاريخ انتهاء العرض ثم مراجعة الموقعين والدفع **النقدي فقط**.
4. تأكيد الرحلة عبر مفتاح `Idempotency-Key` ثابت طوال إعادة محاولة **العملية نفسها**؛ إعادة سعر جديد تولد مفتاحًا جديدًا. نجاح الطلب يُظهر تفاصيل الرحلة من مصدر Trip المشترك نفسه، وليس قائمة ثانية.
5. جميع الخطوات حاليًا **محلية Mock**؛ لا توجد خرائط حية أو GPS أو حجوزات أو خصومات أو تأكيد خلفي.

## شاشة ↔ Repository ↔ API

| شاشة/فعل | عقد المجال | API المقترح |
| --- | --- | --- |
| فتح نافذة اختيار مكان/إدخال بحث | `searchPlaces(query)` | `GET /places?q=...&limit=20&cursor=...` |
| بعد اكتمال موقعين وفئة/تغيير أي منها | `requestQuote(...)` | `POST /ride-quotes` |
| مراجعة الطلب / الضغط على تأكيد / Retry | `confirm(quote, idempotencyKey)` | `POST /trips` |
| فتح التفاصيل بعد نجاح التأكيد | `navigation.openTrip(id)` | عمليات قراءة Trips يملك عقدها الوكيل C |
| اختيار الدفع النقدي | ثابت محليًا، `payment_method=cash` في الطلب المقترح | لا دفع إلكتروني |

**لا تنفذ ضمن هذا العقد:** الجدولة، المحفظة، القسائم، مطابقة السائق، الشات، التتبع، GET /trips، الإلغاء أو تعديل Auth.

## الملفات

- `ride_request-v1.md`: الطلبات والاستجابات والأنواع والقيود والـheaders والأخطاء والـidempotency.
- `ride_request-v1.postman_collection.json`: Postman v2.1 مع طلبات وأمثلة استجابات محفوظة.
- `examples/*.json`: عينات نجاح/فشل وطلب مرتبطة بفئات ومواقع المحاكاة.

### استيراد Postman

استورد Collection ثم اضبط `base_url` ليشمل `/api/v1`، و`access_token` صالحًا **عند توفر خادم**، وغيّر `idempotency_key` لكل محاولة حجز **جديدة**. تسلسل التجربة: البحث عن مكان، عرض سعر، ثم تأكيد باستخدام `quote_id` الساري. لا تحفظ رموزًا أو أسرارًا في المجموعة أو المستودع. العنوان الافتراضي `https://api.example.invalid/api/v1` وهمي عمدًا؛ لا يمكن تنفيذ طلب حي به.

### طريقة الربط المستقبلية

- يبقى `RideRequestRepository` عقد المجال، ويستخدم API adapter منفصل DTO/transport؛ `RideContractParser` يقرأ أمثلة النجاح والأخطاء وفق العقد.
- `FeatureDataModes` المركزي يختار `RIDE_REQUEST_DATA_MODE=api` بعد تنفيذ API والتصديق الحقيقي؛ التنفيذ الحالي لـapi يفشل `SERVICE_UNAVAILABLE` بوضوح دون سقوط إلى mock.
- `MockTripStore` محقون من `TamApp` ومشترك مع «طلباتي» في وضع mock؛ لا تستبدله بمخزن آخر.
- يعتمد الإنتاج على مصادقة حقيقية وتفويض Backend، لا `guest` أو `localAccess`.

## نقاط الاتفاق المفتوحة للباكند والمشرف

- تثبيت سياسات المنطقة والعملات والفئات والأسعار الحقيقية، انتهاء العرض، وتوافر الخدمة.
- اختيار إستراتيجية الإرجاع عند ضياع الاستجابة: نوصي نفس حالة `201` ونفس الجسم عند إعادة نفس المفتاح والطلب، حتى بعد انتهاء العرض إذا كان الحجز قد أنشئ.
- حدود TTL لحفظ مفاتيح idempotency (نقترح 24 ساعة كحد أدنى) وأماكن/ترقيم البحث الحقيقي؛ لا تعتمد المحاكاة المحدودة على قواعد بيانات أماكن حقيقية.
- تثبيت جلسة API وحقوق `GET /places` مقابل حماية التأكيد قبل تشغيل الوضع الحقيقي.

**حدود التحقق:** تنسيق JSON، أمثلة parsing واختبارات Dart محليًا فقط. لا يوجد خادم أو اعتماد عقد من الباكند، ولا اختبار استيراد عبر تطبيق Postman أو استدعاء HTTP حي.
