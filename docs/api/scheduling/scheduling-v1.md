# TAM | تم — عقد جدولة الرحلة v1

الحالة: **مقترح للباكند، غير منفذ أو متحقق حيًا**. التاريخ: 2026-11-09. تحديث إضافي v1 بتاريخ 2026-11-18 للرحلات القادمة.
هذا امتداد صريح لـ[طلب الرحلة v1](../ride_request/ride_request-v1.md)
و[طلباتي v1](../trips/trips-v1.md). يضيف الموعد وحالة scheduled إلى الموارد
نفسها؛ لا مستودع رحلات أو endpoint حجز موازٍ. النسخة الحالية المطلوبة
من الباكند هي العقود السابقة مع هذا الامتداد، لا v1 القديم وحده.

## تدفق المستخدم وقواعد الوقت

1. يختار المستخدم فوريًا أو يفتح نافذة التاريخ والوقت. إغلاق النافذة
   يلغي التعديل المحلي فقط؛ لا طلب API أو حجز عند اختيار التاريخ.
2. الموعد من **30 دقيقة إلى 7 أيام شاملة** من وقت الخادم UTC عند التسعير
   وعند أول تأكيد. إذا انقضى الحد الأدنى أثناء المراجعة، يغير المستخدم الموعد.
3. وقت العرض المعتمد في هذا الإصدار **UTC+03:00** كما في واجهة الخدمة،
   مستقل عن منطقة جهاز العميل. ينقل العميل اللحظة بصيغة UTC ISO-8601 Z،
   ولا يرسل النص المحلي أو AM/PM أو offset جهازه. مثال: 18:00 خدمة = 15:00Z.
   لا يدعي العميل قاعدة IANA ديناميكية أو دعم تغيرات التوقيت الصيفي؛
   تغيير منطقة الخدمة يستلزم مواءمة السياسة المركزية والعقد قبل التشغيل.
4. تغيير الموعد/الفئة/أي موقع يبطل السعر ويطلب عرضًا جديدًا. العودة إلى
   فوري تمسح الموعد وتعيد التسعير. إعادة الطلب تنقل الموقعين فقط وتبدأ فورية.
5. تؤكد الرحلة المجدولة في مصدر الرحلات نفسه وتظهر في القائمة والتفاصيل،
   بحالة scheduled وموعد مستقل عن created_at. لا تعني تعيين سائق الآن.
6. الحجز المجدول لا يغلق إنشاء رحلة فورية؛ يمكن الرجوع للرئيسية لرؤية
   كل الحجوزات القادمة وفتح أي معرف بشكل مستقل ثم طلب رحلة اليوم.
   المحاكاة تسمح بتعدد الحجوزات ولا تفترض كشف تعارض مواعيد أو توافر حي.
   على الخادم تحديد سياسة التعارض قبل الربط؛ لا يستنتج العميل السماح أو
   الرفض النهائي من هذا السلوك التجريبي.

السياسة في Flutter قيمة Domain محقونة وتُركب من AppConfig. الساعة محقونة
للاختبارات. الخادم صاحب الوقت والتوفر والسعر والتأكيد؛ لا تقبل ساعة العميل
كمرجع تفويض. لا HTTP أو سائق فعلي في المحاكاة، ويعمل انتقال الموعد التجريبي فقط وفق [عقد الرحلة الجارية](../active_trip/active_trip-v1.md).
هذه محاكاة محلية وليست إرسال سائق حقيقي أو ضمان تذكير بعد إغلاق التطبيق.

## القواعد المشتركة

`base_url` متغير يشمل `/api/v1`. كل العمليات أدناه محمية بـ
`Authorization: Bearer {{access_token}}`، و`Accept: application/json`،
و`Content-Type: application/json` عند وجود جسم. `Accept-Language: ar|en`
اختياري. guest/localAccess لا يقدمان توكن أو جلسة API.
النجاح data، والقوائم data مع meta.next_cursor، والفشل error.code مع
error.message.ar/en كما في Auth. المعرفات opaque strings غير فارغة.

Location مطلوب وغير nullable: label نص 1..200 بعد trim، latitude/longitude
finite ضمن [-90,90]/[-180,180]؛ الموقعان مختلفان بالإحداثيات. الفئات
standard/comfort/van/motorbike؛ Money بأعداد صحيحة amount_minor>=0،
currency من3 أحرف كبيرة، minor_unit من0 إلى3؛ مثال SYP بوحدة0.
كل التواريخ UTC Z مع تاريخ تقويمي صحيح، لا تسمح بتطبيع 30 فبراير أو hour25.
القيم غير المعروفة خطأ صريح، وليست تحويلًا إلى فوري أو نجاح mock.

## POST /ride-quotes

الجسم كما في `examples/quote-request.json`: pickup وdestination وvehicle_class_id
إلزامية وغير nullable، و**scheduled_at: string|null اختياري**. الغياب أو null
يعني فوريًا للتوافق مع v1. الموعد النصي يجب أن يلتزم بقواعد الوقت أعلاه.
لا تقبل fare من العميل. UI يستخدم دقة الدقيقة؛ العقد يقبل ثواني وأجزاءها
حتى6 منازل في UTC. مقارنة الحدود باللحظة الكاملة، لا تقريب خادمي للموعد.

201 مع data يحوي الحقول المطلوبة في v1: quote_id، الموقعين، الفئة، fare،
distance_meters وduration_minutes أعداد صحيحة موجبة، expires_at UTC Z حصري،
ويضيف scheduled_at string|null. **إلزامي للموعد المجدول** ويطابق لحظة الطلب،
ويجوز غيابه للفوري القديم. id فريد لكل عرض جديد. السعر مرتبط بالموعد أيضًا،
ولا يضمن توفر سائق عند اختياره. TTL في المحاكاة90 ثانية؛ الموعد لا يمدده.

أخطاء خاصة: 422 SCHEDULE_OUT_OF_RANGE، و409 SCHEDULE_UNAVAILABLE حين
لا تتوفر خدمة الجدولة لهذا الوقت. لا يؤكد أي منهما رحلة. أخطاء عامة أدناه.

## POST /trips

الجسم في `examples/confirm-request.json`: quote_id، pickup، destination،
vehicle_class_id، payment_method=cash، وscheduled_at كما في عرض السعر.
حقول v1 إلزامية؛ scheduled_at مطلوب غير null للمجدولة، واختياري/null للفورية.
يتحقق الخادم من التطابق مع quote في الموقعين والفئة والموعد؛ التلاعب لا
يتحول إلى سعر/موعد آخر. لا يستقبل fare. `Idempotency-Key: UUID v4` مطلوب.

201 مع data: Trip بنفس حقول v1، وإضافة scheduled_at string|null؛ المجدولة
تبدأ scheduled، والفورية requested. created_at لحظة الإنشاء، والموعد يجب
أن يكون بعدها. حالة scheduled دون موعد أو موعد بتاريخ غير صالح خطأ استجابة.
يحفظ الموعد مع المورد حتى بعد الإلغاء أو تغير حالته، ولا يعاد حسابه من الجهاز.

قبل **أول أثر**: يتحقق الخادم ذريًا من الهوية والملكية وquote وصلاحيته
والتطابق وحدود الوقت والتوفر. أي رفض خاص بالجدولة أدناه يجب أن يعني
عدم إنشاء رحلة حتى يستطيع العميل فتح التعديل بأمان.

### إعادة المحاولة ومنع التكرار

- يحتفظ الخادم بنتيجة `(user_id, Idempotency-Key, normalized_body)` ذريًا
  لمدة24 ساعة على الأقل. يدخل الموعد UTC المطبع وquote_id في هوية الجسم.
- نفس المفتاح والجسم يعيدان **نفس id والمورد الحالي المملوك للمستخدم**
  دون إنشاء، حتى إن انتهى السعر أو الموعد أو تغير التوفر بعد نجاح أول
  محاولة. إذا ألغيت الرحلة لاحقًا يعود المورد cancelled مع الموعد نفسه.
  هذا يوضح نتيجة retry بعد تغير الحالة، ولا يعيدها إلى scheduled.
- جسم مختلف مع المفتاح نفسه:409 IDEMPOTENCY_CONFLICT، دون إنشاء جديد.
  انتهاء quote قبل أول إنشاء:410 QUOTE_EXPIRED. تغير الموعد يحتاج quote
  ومفتاحًا جديدين بعد حسم أي تأكيد سابق.
- timeout/503/خطأ غير حاسم يقفل المواقع والفئة والموعد وإعادة التسعير؛
  يعاد نفس الطلب والمفتاح حتى يحسم. لا يحوّل العميل إلى فوري ولا يكرر الرحلة.
- 410 QUOTE_EXPIRED أو422 SCHEDULE_OUT_OF_RANGE أو409 SCHEDULE_UNAVAILABLE
  أو422 VALIDATION_ERROR رفض نهائي قبل الإنشاء؛ يعرض العميل الخطأ ويفتح
  التعديل وإعادة التسعير. لا يستخدم الباكند هذه الأكواد بعد أثر غير محسوم.

## قائمة الرحلات والتفاصيل والإلغاء

- GET /trips?filter=active&limit=20:200، active يضيف scheduled إلى requested /
  confirmed / in_progress. filter=all|active|completed|cancelled|scheduled، limit1..50
  افتراضي20، cursor opaque اختياري. created_at DESC ثم id ASC كما في v1؛
  meta.next_cursor مطلوب nullable.
- امتداد v1 الإضافي: GET /trips?filter=scheduled&sort=scheduled_at_asc&limit=20
  يعيد فقط scheduled المملوكة للحساب، مرتبة scheduled_at ASC ثم id ASC،
  مع cursor ثابت على هذا الترتيب وmeta.next_cursor. يعرض العميل جميع الصفحات
  في قائمة الرئيسية؛ لا يكتفي بأول حجز ولا يعتمد ترتيب created_at للجدولة.
  قيم sort غير المعروفة أو sort=scheduled_at_asc مع filter غير scheduled:
  422 VALIDATION_ERROR. عند عدم وجود حجوزات: data: [] لا خطأ.
  الإلغاء يزيل المعرف الملغى فقط من هذه القائمة؛ يبقى المورد قابلًا للتفاصيل
  مع scheduled_at المحفوظ. لا endpoint موازٍ لإنشاء الحجز.
- GET /trips/current ضمن عقد الرحلة الجارية يستثني scheduled ويختار الرحلة
  الفورية/الموزعة فقط. يمكن أن يعيد null مع وجود حجوزات قادمة؛ لا يمحوها.
  GET /trips/{id} يفتح الحجز المختار، حتى مع وجود رحلة فورية أخرى.
- GET /trips/{id}:200 مع Trip وscheduled_at المحفوظ. غير الموجود أو غير
  المملوك:404 TRIP_NOT_FOUND؛ القائمة خاصة بالحساب، لا تسرب موارد الآخرين.
- POST /trips/{id}/cancel: بلا جسم، scheduled تضاف للحالات القابلة للإلغاء
  requested/confirmed.200 مع cancelled والموعد نفسه؛ تكرار الإلغاء يعيد
  نفس المورد دون أثر ثانٍ. in_progress/completed:409 TRIP_NOT_CANCELLABLE.
- تعديل الموعد **بعد الحجز** غير مدعوم في هذا الإصدار؛ المستخدم يلغي ويبدأ
  طلبًا جديدًا. الانتقال إلى طلب سائق قرب الموعد موصوف في عقد الرحلة الجارية؛
  لا يعني عرض الموعد قبول خادم حي أو ضمان توافر سائق.

## الأخطاء وأمثلتها

كل عملية تتعامل مع401 UNAUTHENTICATED و403 FORBIDDEN و429 RATE_LIMITED
و503 SERVICE_UNAVAILABLE و500 INTERNAL_ERROR.401 هو كود Auth الموحد لهذا
الامتداد؛ يوضح اختلاف التسمية UNAUTHORIZED في وثيقة Trips القديمة قبل الربط.
JSON المعطوب400، والحقول/الفلاتر غير الصالحة422 VALIDATION_ERROR.
التفاصيل404 والإلغاء409 كما أعلاه؛ تأكيد السعر410، وتعارض المفتاح409.
الحزمتان لا تعدان حماية UI بديلًا عن تفويض كل طلب في Laravel.

`examples/error-*.json` وSaved responses في Postman تحتوي أمثلة ثنائية اللغة
لكل الأكواد المذكورة؛ الرسائل ليست مصدر قواعد العميل. payload الفشل لا يحتوي data.

## المطابقة والتحقق وحدود التسليم

أمثلة الساعة الثابتة: now=2026-11-09T12:00Z، الموعد15:00Z، انتهاء السعر12:01:30Z.
تعيد المحاكاة نفس مواقع Ride و5019 مترًا و18 دقيقة و27000 SYP؛ هذه بيانات
اصطناعية وليست قياس طريق أو تسعيرًا حيًا. مصدر الرحلات واحد محقون للجلسة،
وتُحفظ الحجوزات التجريبية في snapshot محلي مملوك لجلسة واحدة لاستعادة العملية
بعد إعادة تشغيل التطبيق؛ تبديل المالك أو الخروج يمسحه. لا بيانات اعتماد أو
جلسة backend داخل snapshot، ولا تذكير نظام أو إشعار مضمون بعد الإغلاق.
الحجز الفوري والمجدول يستخدمان MockTripStore نفسه؛ الإلغاء لا يمس الحجوزات الأخرى.
فشل استعادة snapshot أو حفظه يُبلغ كتعذر خدمة ولا يتحول إلى نجاح صامت.
اختبارات العقد تقارن parsing والـmock وأمثلة Postman. صلاحية JSON لا تعني
استيراد واجهة Postman أو طلب خادم ناجح؛ يسجل تقرير التسليم ما نفذ فعليًا.

| واجهة/فعل | Domain/Data | العملية |
|---|---|---|
| اختيار موعد/فوري | RideSchedulePolicy وRideScheduleChanged | تعديل محلي ثم إعادة التسعير إن اكتمل المسار |
| عرض السعر | RideRequestRepository.requestQuote(scheduledAt) | POST /ride-quotes |
| تأكيد/إعادة محاولة | confirm(quote,idempotencyKey) | POST /trips |
| القائمة/التفاصيل | TripsRepository | GET /trips وGET /trips/{id} |
| حجوزات الرئيسية القادمة | UpcomingTripsRepository.upcoming | GET /trips?filter=scheduled&sort=scheduled_at_asc (مع تجميع الصفحات) |
| إلغاء | TripsRepository.cancel | POST /trips/{id}/cancel |

قبل الربط الإنتاجي يثبت الباكند TTL ومدة حفظ المفاتيح والوقت المعتمد وسياسة
التوفر، ويطبق dispatch والإشعارات ضمن عقد الرحلة الجارية لاحقًا. موافقة
المرحلة الأولى لا تعني حجزًا فعليًا أو جاهزية نشر.
