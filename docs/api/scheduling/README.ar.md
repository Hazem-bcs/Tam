# حزمة جدولة الرحلات — إلى مطور الباكند

الانتقال عند الموعد والمتابعة أصبحا ضمن [امتداد الرحلة الجارية](../active_trip/active_trip-v1.md)؛
لا يبقى الحجز المجدول scheduled إلى الأبد أثناء تشغيل المحاكاة.

اقرأ [العقد العربي](scheduling-v1.md)، ثم استورد
`scheduling-v1.postman_collection.json` كـCollection v2.1.
هذه مواصفات تنفيذ مقترحة، ولا يوجد خادم متصل بها حاليًا.

1. اضبط base_url شاملاً /api/v1، وaccess_token لجلسة Auth حقيقية.
2. أنشئ عرض سعر من الطلب01 بعد تغيير scheduled_at إلى UTC Z بين
   30 دقيقة و7 أيام من وقت الخادم؛ أوقات Saved responses ثابتة للاطلاع.
3. مرر quote_id والمواقع والفئة والموعد الراجعة إلى الطلب02، مع مفتاح
   operation_id جديد لكل نية حجز. لا تغيره أو الجسم عند إعادة محاولة timeout.
4. شاهد القائمة النشطة والتفاصيل ثم الإلغاء؛ الموعد يبقى بعد الإلغاء.
5. راجع Saved responses والأمثلة للنجاح والفراغ والحدود والتوفر والفشل.

توقيت الخدمة المعتمد لهذا الإصدار UTC+03:00؛ النقل والحفظ UTC. لا تفسر
scheduled_at كتاريخ محلي في منطقة جهاز أو خادم التشغيل. موعد18:00 خدمة
يعادل15:00Z. السعر مرتبط بالموعد والتغيير يحتاج إعادة تسعير.

هذه الحزمة توسع عمليات Ride/Trips القائمة، ولا تطلب API موازيًا أو تعديل
Auth. حالة scheduled لا تعني تعيين سائق الآن؛ dispatch والتتبع لاحقًا.
الدخول المحلي والضيف في Flutter ليسا توكن API. الأمثلة اصطناعية وبلا أسرار.
الحفظ في المحاكاة ذاكرة جلسة فقط؛ لا ادعاء ربط حي أو استيراد واجهة Postman.
