# طلباتي — تسليم واجهة الباكند v1

امتداد التنفيذ الحالي: [الرحلة الجارية v1](../active_trip/active_trip-v1.md)
للحالات وبيانات live والإلغاء الذري والمتابعة من المصدر نفسه.

## امتداد الجدولة الحالي

للتنفيذ الحالي اقرأ أيضًا [عقد الجدولة v1](../scheduling/scheduling-v1.md):
حالة scheduled وموعد الرحلة في القائمة والتفاصيل والإلغاء.

**الحالة: عقد مقترح للتنفيذ، وليس API قائمًا أو مُختبرًا حيًا.**

هذه الحزمة تخص رحلات العميل في تطبيق «تم»: قائمة الرحلات بفلاتر وترقيم cursor، التفاصيل، وإلغاء رحلة مسموح إلغاؤها. تعمل واجهة Flutter الآن بمحاكاة محلية باستخدام `MockTripStore` المشترك مع الحجز. لا تُرسل حجوزات أو إلغاءات إلى خادم.

## الربط المطلوب

| فعل العميل | Flutter domain | العملية المقترحة |
|---|---|---|
| فتح «طلباتي»، تغيير الفلتر، تحديث/المزيد | `TripsRepository.list` | `GET /trips` |
| فتح تفاصيل رحلة، أو فتح رابط مباشر | `TripsRepository.find` | `GET /trips/{id}` |
| إلغاء رحلة بعد تأكيد العميل | `TripsRepository.cancel` | `POST /trips/{id}/cancel` |
| «اطلب مجددًا» | `TripPrefill(pickup, destination)` | **لا يوجد endpoint هنا**؛ يفتح ميزة الحجز الجديدة (B) لطلب عرض سعر حديث |

المسارات نسبية إلى `base_url` المتضمنة `/api/v1`، مثال تنموي `https://api.example.invalid/api/v1` لا يمثل خادمًا حقيقيًا. المصادقة الحقيقية `Authorization: Bearer <access_token>` إلزامية للخادم؛ `localAccess` وguest في وضع mock ليست جلسات موثّقة.

العقد الفني: [trips-v1.md](trips-v1.md). ملفات الأمثلة في `examples/`، ومجموعة Postman قابلة للاستيراد بصيغة v2.1: [trips-v1.postman_collection.json](trips-v1.postman_collection.json).

## تشغيل Postman

استورد المجموعة، وعدّل `base_url` إلى خادمك الحقيقي و`access_token` إلى رمز اختبار مأذون (لا تخزّن أسرارًا في Git). استخدم أولًا `GET /trips`، ثم انسخ `id` إلى `trip_id`، ثم جرّب التفاصيل وإلغاء رحلة تجريبية بحالة `requested` أو `confirmed`. يمكن استخدام `next_cursor` المردود فقط لطلب الصفحة التالية، ولا يُحلّل في العميل.

Postman يحتوي Saved Responses للنجاح والفراغ والإخفاق؛ إنها بيانات **محاكاة تركيبية** وليست نتائج طلبات خادم. لا يُفترض أن استيراد JSON أو نجاح unit tests يثبت اتصالاً حيًا.

## مسؤوليات الخادم وملاحظات التكامل

- فرض ملكية الرحلة وجلسة Auth صالحة على كل العمليات؛ عدم كشف رحلات عملاء آخرين.
- إرجاع الحقول المشتركة نفسها مع B: `id/pickup/destination/vehicle_class_id/fare/status/created_at`.
- ترتيب `created_at DESC, id ASC`، مع cursor معتم وثابت منطقيًا خلال التصفح وإزالة تكرار العناصر في العميل أيضًا.
- معاملة الإلغاء ذرية: `requested/confirmed` فقط؛ تكرار إلغاء `cancelled` يعيد الرحلة الملغاة دون أثر ثانٍ؛ `in_progress/completed` => 409.
- إرسال أحداث تغيير الرحلات أو استراتيجية تحديث عند توفر backend لاحقًا؛ المحاكاة حاليًا تعتمد على `MockTripStore.changes`. **لم يتحدد** realtime transport أو cache invalidation للخادم بعد؛ واجهة API المقترحة تعتمد تحديثات صريحة عند فتح/refresh.
- لا يوجد GPS أو سائق حقيقي أو دفع أو زمن وصول أو خريطة مؤكدة في نطاق C. بيانات الصور الأمثلة اصطناعية.

التحقق المستقل الواجب عند توفر الخادم: الصلاحيات 401/403، استقرار cursor أثناء الإدراج، سباق إلغاء رحلتين، تجديد الجلسة، أخطاء الشبكة وإعادة المحاولة، توافق JSON مع `TripWireCodec` وFlutter، والتحقق من السيناريوهات باللغتين.
