# TAM | تم — العقد الموحد لتطبيق العميل v1

الحالة: **مقترح مُراجع صالح لتسليم الباكند، لا API حي ولا اعتماد باكند بعد**.
هذا الملف طلب تنفيذ من مطور Laravel. نكمل منطق العميل بالمحاكاة وعقوده،
نسلّم Collection موحدة، ثم نحسن الواجهات أثناء تنفيذ الخادم. الربط الحقيقي
واختبار الخدمات يأتيان عند تسليم الباكند؛ لا يشترطان لبدء الصقل البصري.

## النطاق المعتمد

المصادقة، الرئيسية، البحث والتسعير والحجز النقدي، الجدولة، طلباتي والإلغاء
وإعادة الطلب، العناوين، متابعة الرحلة، المحادثة، التقييم، الدعم والبلاغات،
الإشعارات داخل التطبيق، إعدادات الحساب، تغيير الرقم وحذف الحساب والاتصال
بالسائق. المحفظة والدفع الإلكتروني والكوبونات مؤجلة بقرار المستخدم.
لا طعام أو تسوق أو أدوار سائق وإدارة داخل هذا العميل. payment_method=cash
لا يثبت تحصيلًا أو إيصالًا، ولا توجد عملية دفع خادمية مختلقة.

قبول الرحلة وإسناد سائق ووصوله وبدؤها وإنهاؤها وموقعه مسؤولية الخادم
والسائق؛ ليست أوامر من تطبيق الراكب. تنفيذ الجدولة عند الموعد مسؤولية
الخادم حتى لو كان العميل مغلقًا. المحاكاة لا تنفذ عملًا خلفيًا حقيقيًا.

## القواعد المشتركة

- base_url يشمل /api/v1 مرة واحدة؛ example.invalid قيمة توضيحية.
- النجاح data؛ الفشل error.code وerror.message.ar/en، دون الجمع بينهما.
- UTF8، معرفات opaque نصية، والوقت ISO8601 UTC Z بتقويم صحيح. عرض الجدولة
  UTC+03:00 والمدخل المنقول UTC؛ النطاق من30 دقيقة إلى7 أيام.
- المال amount_minor:int≥0 وcurrency كبيرة3أحرف وminor_unit:int0..3.
  أمثلة SYP بوحدة0؛ لا float ولا سعر نهائي من جهاز العميل.
- Bearer للبيانات والعمليات الشخصية؛ guest/localAccess ليسا مصادقة API.
  /home و/places و/content/legal عامة. مسارات Auth تتبع عقدها الأصلي؛
  /auth/me محمي، وrefresh/logout يستخدمان refresh_token كما في العقد.
- للميزات 401 UNAUTHENTICATED؛ استبدل الاسمين القديمين AUTH_REQUIRED
  وUNAUTHORIZED في Settings/Trips. أكواد Auth التفصيلية SESSION_INVALID
  وSESSION_REVOKED تبقى كما هي؛ لم يُغير عقد Auth.
- الملكية تفحص في كل عملية. يجوز404 للمورد الأجنبي بدل403 بسياسة ثابتة،
  دون كشف بياناته. فشل الخدمة لا يعود إلى mock.
- عمليات الإنشاء تطبق idempotency وفق عقدها. timeout ليس رفضًا نهائيًا؛
  لا تبديل للنية أو المفتاح بعد فقد رد غير محسوم.

## Trip واحد وامتدادات متوافقة

الحجز وطلباتي والجدولة والمتابعة تستخدم المورد نفسه. دورة الحالات:

scheduled → requested → confirmed → driver_en_route → driver_arrived →
in_progress → completed. قد تصبح requested حالة no_driver.

يسمح إلغاء العميل في scheduled/requested/confirmed/driver_en_route/
driver_arrived. تكرار إلغاء cancelled آمن؛ بقية الحالات409
TRIP_NOT_CANCELLABLE دون رسوم مختلقة. active يشمل الحالات الست غير النهائية،
وno_driver يظهر في all.

scheduled_at مطلوب للمجدولة ويظل محفوظًا بعد الإلغاء وتغيّر الحالة؛ غيابه
أوnull للفوري القديم مسموح. live مطلوب لمسارات المتابعة، واختياري للسجلات
القديمة في Trip. active_trip-v1 يحدد الحالة الموسعة كاملة؛ الامتدادات الحالية
تحدث قيود W1 القديمة ولا تطلب مخزن رحلات أو إلغاء آخر لكل شاشة.

fare مبلغ الطلب المسجل، وليس تأكيد دفع. بيانات السائق والموقع وETA من live؛
موقع وETA الحالات النهائية null. التقييم مورد واحد immutable لرحلة completed.
الاتصال مورد مستقل قصير الصلاحية للسائق الحالي؛ لا رقم هاتف في history.

GET /places مشترك للحجز والعناوين. POST /ride-quotes وPOST /trips يدعمان
الفوري والمجدول بنفس المسارات، مع أمثلة سيناريوهات منفصلة. تكرار GET detail
أوPOST cancel في المجلدات يشرح حالات استخدامها، ولا يعني endpoint جديدًا
في Laravel لكل مجلد.

الترقيم بحسب المورد، دون تحويل صامت: Trips/Places/Notifications تستخدم
قائمة data وmeta.next_cursor؛ Support تستخدم data.tickets وpagination.
الحدود والترتيب موثقة في كل عقد وتطابق Flutter. أي توحيد لاحق يحتاج تغيير
العقد والـmappers والأمثلة معًا.

## الحساب والاتصال

تغيير الرقم والحذف يحتاجان OTP مستقلًا عن الدخول، مع منع رحلة غير منتهية.
التغيير يتحقق من الرقم الجديد، والحذف من الحالي مع موافقة صريحة. النجاح
ينهي الجلسة ولا يصدر توكنًا جديدًا. راجع account_management-v1 للحدود
والتحقق الذري والقفل وidempotency وحسم فقد الرد.

X-Operation-Token اعتماد ضيق لنتيجة عملية واحدة، وليس جلسة أوBearer. لا
ينفذ أول تعديل دون Bearer وOTP صالحين. يتيح استرجاع نتيجة نفس العملية
بعد إبطال الجلسة أو فقد الرد. GET /account/operations/{operation_id} يحتاج
هذا الاعتماد ولا يكشف بيانات حساب؛ يخزنه محول API خصوصيًا في data، لا في
URL أوlogs أوBLoC state.

الاتصال يقرأ رقمًا مخولًا للرحلة والسائق الحاليين، ثم يفتح تطبيق الهاتف.
لا URL حر ولا اتصال مباشر دون تطبيق الهاتف، ولا ادعاء رد السائق أوفوترة.
المحاكاة لا تطلب رقم fixtures فعليًا. النص القانوني غير المنشور يعيد null؛
لا نصوص قانونية مولدة أو إقرار موافقة مخترع. اللغة إعداد محلي بلا endpoint.

## كيفية قراءة ملف Postman

الملف Tam-Customer-API-v1.postman_collection.json مقسم حسب الميزة. وصف
المجموعة يحتوي هذا النص، ووصف كل مجلد يحتوي عقد الميزة كاملًا، وتحت كل
طلب Headers وBody وAuthorization وأمثلة نجاح وفشل. لا يحتاج المطور قراءة
كود Flutter لمعرفة الحقول والقيود.

المتغيرات التخصصية تبدأ باسم الميزة لمنع تداخل challenge_id أومفاتيح
idempotency أوcursor؛ base_url وaccess_token وlanguage مشتركة. لا أسرار أو
scripts تشغل طلبات تلقائيًا. الأمثلة اصطناعية؛ لا تستخدم أرقامها كجهات اتصال.

نحتاج من الباكند: staging URL، تنفيذ العقود والملكية والحفظ، مصادقة وSMS
اختبار، تحقق ذري للحجز والسعر والوقت والحالات ومنع التكرار، مصدر حالة
وموقع السائق والمحادثة، واختبارات Laravel لكل نجاح وفشل مطلوب. جهة routing
تحدد مزود المسار والبحث؛ لا مفاتيح مزود سرية داخل Flutter.

العميل الحالي يستخدم polling للمتابعة والمحادثة وصندوق إشعارات داخل
التطبيق. Push/FCM وتسجيل الجهاز والتسليم بالخلفية وSDK المواقع والخرائط
واختبار تطبيق الهاتف على جهاز فعلي أعمال ربط خدمات تنسق عند جاهزيتها؛
ليست منفذة لمجرد وجود واجهة أو مثال. لا endpoint جهاز مختلق في هذا الإصدار.

## معيار الاعتماد

نفحص JSON وبنية Postman2.1 ومراجع المتغيرات والتفويض والأمثلة والمحاكاة
والـmappers والتدفقات المتكاملة. الاعتماد المستقل مرتبط بـSHA الكود والعقود
في [تقرير المراجعة](../engineering/deliveries/W3-ACCOUNT-CONTACT/REVIEW.md)،
ويُعاد عند تغيير النسخة. فحص JSON لا يساوي استيراد Postman أو طلبًا حيًا.
هذا المقترح لا يدعي اكتمال الربط أو جاهزية النشر. التحسين البصري لاحق؛ إذا أضاف تغيير
التصميم قاعدة عمل أوحقلًا جديدًا، ينسق تعديل العقد صراحة.
