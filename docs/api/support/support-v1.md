# TAM | تم — عقد الدعم والمحتوى القانوني v1

الإصدار1.0، 2026-11-09. **مقترح للتنفيذ؛ لا يوجد خادم حي متصل.**
هذا الملف يحدد المطلوب من الباكند ولا يغيّر عقد المصادقة القائم.

## التدفقات والعمليات

| الشاشة أو الفعل | Repository | HTTP بالنسبة إلى base_url |
|---|---|---|
| فتح نموذج عام أو بلاغ رحلة | options(tripId?) | GET /support/options?trip_id=… |
| طلباتي للدعم، تحديث، تحميل المزيد | tickets(cursor?) | GET /support/tickets?limit=20&cursor=… |
| تفاصيل طلب للقراءة | ticket(id) | GET /support/tickets/{id} |
| إرسال النموذج أو إعادة محاولة نفس الطلب | create(...) | POST /support/tickets |
| الشروط أو الخصوصية | legal(kind,languageCode) | GET /content/legal/{kind}?language=ar\|en |

base_url مثال `https://example.invalid/api/v1`. يُرسل Accept:application/json؛
POST كذلك Content-Type:application/json. كل مسارات /support تتطلب
Authorization:Bearer والتفويض لمالك الحساب في **كل عملية**. لا يكفي امتلاك
معرّف الرحلة أو الطلب. guest/localAccess ليسا جلسة باكند. /content/legal عام
بلا Authorization؛ لا تُشترط المصادقة لقراءة نص منشور.

النجاح `{"data":...}` والفشل `{"error":{"code":"…","message":{"ar":"…","en":"…"}}}`.
لا يجتمع data وerror. معرّفات الموارد opaque nonempty strings وليست أسماء
أشخاص. التواريخ ISO8601 UTC تنتهي بـZ. revision عدد صحيح يبدأ من1 ويتزايد
مع تغيّر المورد؛ نفس revision يعني نفس المحتوى. النصوص تُعرض plain text.

## الفئات والسياق

GET /support/options يعيد data.trip_id:string|null وdata.categories:list.
كل فئة تحتوي id:string وname:{ar:string,en:string} وtrip_required:bool.
المعرّفات فريدة، والأسماء غير فارغة. بدون trip_id تعاد فقط الفئات العامة.
مع trip_id يتحقق الخادم من الملكية والوجود، ويعيد الفئات المسموحة في السياق
العام وسياق الرحلة. يعيد trip_id نفسه. لا توجد قائمة رحلات موازية في الدعم.

فئات المحاكاة المرجعية: general وapp_issue لا تتطلبان رحلة؛ trip_issue
تتطلب رحلة. الكتالوج مصدره الخادم؛ العميل لا يفترض حصر الفئات بهذه الثلاث.
المحاكاة تختار أول فئة افتراضيًا ويستطيع المستخدم تغييرها.

## إنشاء طلب وإعادة المحاولة

POST body:

```json
{
  "client_request_id": "request-0000000001",
  "category_id": "trip_issue",
  "body": "Details of the issue",
  "trip_id": "trip-1"
}
```

client_request_id مطلوب ASCII مطابق `[A-Za-z0-9_-]{16,128}`؛ ينتج العميل
48 حرفًا hex من Random.secure. ليس مشتقًا من ساعة الجهاز. category_id
مطلوب من الكتالوج المسموح. body مطلوب string بعد trim بطول10..2000 Unicode
code points، لا UTF16 units ولا bytes. لا تُقص البيانات بصمت. trip_id اختياري
nullable؛ إذا كانت الفئة trip_required فهو مطلوب. أي رحلة مُرسلة يجب أن
تكون للحساب الحالي، حتى عندما تكون الفئة عامة. لا مرفقات في الإصدار1.

الخادم ينفذ ذريًا: التفويض والتحقق ثم إنشاء تذكرة واحدة لكل
(account,client_request_id). أول نجاح201؛ إعادة نفس البيانات المطبعة200
بنفس المورد. نفس المعرّف ببيانات مختلفة409 IDEMPOTENCY_CONFLICT، دون إنشاء
طلب ثانٍ أو تعديل الأول. تُحفظ رابطة idempotency طوال بقاء التذكرة، دون
نافذة انتهاء أقصر منها. اختلاف الفئة أو trip_id أو النص المطبّع تعارض.
تعاد التذكرة الحالية إن تغيّرت حالتها لاحقًا؛ هوية الطلب ومحتوى إنشائه ثابتة.

انقطاع الشبكة ليس إثبات رفض: العميل يقفل الحمولة ويعيد نفس المعرّف، أو
يتحقق من القائمة/التفاصيل عبر client_request_id. لا يفترض الوصول من أول
صفحة دليلًا على غياب الطلب. لا endpoint بحث خاص ولا outbox دائم في النطاق.
عند الخروج أو إغلاق النموذج تزول المسودة المحلية؛ المقبول يستعاد من
Repository داخل الجلسة، ومن الخادم للحساب عند الربط الحقيقي.

## شكل التذكرة والقائمة

الاستجابة للتفاصيل والإنشاء data كائن يتضمن:

| الحقل | النوع والقيود |
|---|---|
| id | string غير فارغ، ثابت |
| client_request_id | string وفق النمط السابق، ثابت |
| category_id | string غير فارغ، ثابت |
| body | string مطبّع10..2000 code points، ثابت |
| trip_id | string أوnull، ثابت |
| status | open أوin_progress أوresolved |
| created_at | UTC، ثابت |
| updated_at | UTC، لا يسبق created_at |
| revision | int≥1، يزداد مع تغيّر الحالة |

العميل يقرأ الحالات فقط؛ لا تعديل أو إغلاق أو مراسلة دعم ضمن هذا الإصدار.
الجديد open. المحاكاة لا تدّعي معالجة فريق حقيقي. لا وعود استجابة أو SLA
أو جهات اتصال مختلقة. أمثلة الحالات الأخرى لشرح استجابات الباكند واختبارها.

GET /support/tickets يعيد data.tickets:list وdata.pagination:
`{"limit":20,"next_cursor":null}`. limit افتراضي وثابت20؛ غيره422.
الترتيب created_at تنازليًا ثمid تنازليًا عند التعادل، بمقارنة معرّف ثابتة
متفق عليها كترتيب ASCII للأمثلة. لا تكرار معرفات داخل الصفحة أو بين صفحات
المتابعة. cursor opaque مرتبط بالحساب وبآخر عنصر مرتب، دون offset؛ إدراج
طلب أحدث لا يكرر أو يسقط الأقدم أثناء المتابعة. قد تتغير حالة عنصر قديم،
لكن لا يُنقل بسبب updated_at. لا تكشف cursor حساب آخر؛422 INVALID_CURSOR.
next_cursor لا يكون غيرnull إلا إذا كانت الصفحة20 ويوجد المزيد.
المحاكاة تستخدم base64url لمؤشر جلسة/معرّف؛ لا يشترط تقليد ترميزه في الخادم.

## المحتوى القانوني العام

kind=terms|privacy وlanguage=ar|en، مطلوبان وصالحان؛ خلاف ذلك422.
إذا لم ينشر صاحب المنتج نصًا معتمدًا للنوع واللغة:200 `{"data":null}`.
لا نص بديل مولّد ولا ادعاء موافقة. عند نشر نص معتمد فقط تكون data:
kind وlanguage وplain_text وversion نصوص غير فارغة وpublished_at بتوقيتUTC.
plain_text نص بلا HTML أو سكربت أو تشغيل روابط. يُعاد النوع واللغة المطلوبان
تمامًا؛ لا fallback صامت للغة أخرى. لا أحداث موافقة أو تغييرات Auth هنا.
لا توجد أمثلة قانونية منشورة في الحزمة لأن النص المعتمد لم يُسلّم بعد.

## الأخطاء

| HTTP | code | السياق |
|---|---|---|
| 401 | UNAUTHENTICATED | جلسة مفقودة/منتهية في الدعم |
| 403 | FORBIDDEN | منع الوصول إلى مورد أو سياق |
| 404 | TRIP_NOT_FOUND | رحلة مفقودة أو مخفية بسياسة الملكية |
| 404 | TICKET_NOT_FOUND | طلب مفقود أو مخفي بسياسة الملكية |
| 409 | IDEMPOTENCY_CONFLICT | معرّف مكرر ببيانات مختلفة |
| 422 | VALIDATION_ERROR | أنواع/أطوال/لغة/kind/limit/معرّف غير صالح |
| 422 | INVALID_CATEGORY | فئة مجهولة أو غير مسموحة بالسياق |
| 422 | INVALID_CURSOR | مؤشر غير صالح/سياق حساب مختلف |
| 429 | RATE_LIMITED | الحد المؤقت؛ Retry-After عند توفره |
| 503 | SERVICE_UNAVAILABLE | خدمة غير متاحة |

لا تعاد أخطاء مصادقة على مسار المحتوى العام لمجرد عدم وجود جلسة. يجوز
إخفاء الموارد الأجنبية404 بدل403 لمنع كشف الوجود، مع ثبات السياسة وعدم
تسريب نصوصها. NETWORK_ERROR/INVALID_RESPONSE/SESSION_ENDED إخفاقات محلية،
لا حالات نجاح من الخادم. لا fallback من API إلىmock عند خطأ.

## مسؤوليات التسليم والتحقق

الباكند مسؤول عن الملكية والتخزين والتزامن وidempotency والوقت وحالات
الموظفين والنص المعتمد. Flutter مسؤول عن التحقق المبدئي والحمولة الثابتة
والترجمات وعرض الحالات وعزل الجلسات. AppConfig يملك اختيار المصدر والسياسة؛
لا HTTP adapter فعلي بعد. أي تغيير للحدود أو الحقول ينسق مع Flutter قبل
اعتماد الإصدار. اختبارات support_contract_test تربط الأمثلة بالـmapper
والمحاكاة وPostman؛ لا يُعد ذلك تحققًا حيًا أو استيرادًا فعليًا في Postman.
