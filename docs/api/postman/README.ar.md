# تم — تسليم API تطبيق العميل

الملف الموحد: **Tam-Customer-API-v1.postman_collection.json**.
الحالة **REVIEW_REQUIRED**: أضيف امتداد الخرائط وينتظر اعتماد نسخته الجديدة.
فُحص الكود والعقود والأمثلة مستقلًا؛ الاعتماد مرتبط بالنسخة المحددة في
[تقرير المراجعة](../../engineering/deliveries/W3-ACCOUNT-CONTACT/REVIEW.md).
لا يعني ذلك موافقة مطور الباكند أو خادمًا حيًا أو جاهزية نشر.

## الملف الذي يقرأه مطور الباكند

استورد الملف الواحد في Postman، وافتح وصف المجموعة أولًا: العقد العربي
الموحد موجود فيه كاملًا. كل مجلد يضم عقد الميزة كاملًا في وصفه، والطلبات
والـheaders وbody وauth وsaved response examples. لا يحتاج المطور قراءة
كود Flutter أو البحث بين ملفات متفرقة لفهم المتطلبات.

15 مجلدًا و62 مثال طلب؛ تكرار المسار في سيناريوهات الجدولة/المتابعة/التاريخ
لا يعني62 endpoint منفصلًا. أساس Trip واحد. Auth مشمول مرة واحدة دون
إدراج نسخة الحزمة المؤرشفة مرة ثانية.

النطاق: الرحلات وميزات العميل الحالية، مع تغيير الرقم وحذف الحساب والاتصال
بالسائق. الدفع الإلكتروني والمحفظة والكوبونات مؤجلة. تدفقات المحاكاة
مفصولة عن المصادقة الحقيقية، ولا ترسل حجوزات أوSMS أوأرقام اتصال فعلية.

## المتغيرات وتسلسل التجربة

- base_url يشمل /api/v1؛ الافتراضي example.invalid توضيحي فقط.
- access_token فارغ؛ ضع توكن staging مخولًا عند جاهزية الخادم.
- language=ar أوen. بقية المتغيرات لها بادئات الميزة: auth_ وride_ وschedule_
  وaccount_ وcontact_ وغيرها، حتى لا يتصادم رمز OTP أومفتاح عملية من ميزة أخرى.
- اقرأ المتغير في URL/Body، وانسخ القيمة المطلوبة من استجابة الخادم. لا توجد
  scripts تحفظ التوكن أو تنفذ طلبات تلقائيًا. الأمثلة ليست حسابات فعلية.

التسلسل: OTP ثم verify، ثم Home/الأماكن، ثم quote وconfirm، ثم trips/current
وlive، ثم المحادثة أوالاتصال، ثم completion/rating/support. الجدولة سيناريو
لنفس الحجز. تغيير الرقم والحذف عمليتان حساستان تنهيان الجلسة؛ جربهما على
حساب staging منفصل بعد قراءة قواعد OTP وX-Operation-Token المحدود.

بعد فقد الرد أعد نفس معرّف العملية والحمولة، ولا تنشئ حجزًا أوتقييمًا أوطلب
دعم آخر. GET receipt لإدارة الحساب يحتاج اعتماد الاستعادة حتى بدون Bearer،
ولا يسمح بتنفيذ أول أثر بلا جلسة موثقة. لا تشارك نسخة تحتوي توكنًا حقيقيًا.

## مصادر العقد وإعادة التوليد

العقد الموحد في docs/api/customer-api-v1.md، والعقود الأصلية في مجلدات
الميزات. customer-api-v1.manifest.json يسجل أسماء المصادر وبصماتها وعدد
الأمثلة. التوليد حتمي، ويكشف تغير مصدر دون إعادة تجميع:

```bash
python3 scripts/api/build_customer_postman.py
python3 scripts/api/build_customer_postman.py --check
python3 -m unittest discover -s scripts/api/tests -v
```

فُحصت JSON والـsaved responses وauth والمتغيرات ومطابقة المصادر آليًا.
لم يُنفذ استيراد فعلي داخل Postman أو طلب حي. مراجعة الكود والعقود والأمثلة
وفحوصها موثقة في تقرير المراجعة؛ أي تغيير لاحق يحتاج مراجعة النسخة الجديدة.
بعد التسليم يبدأ تحسين الواجهات؛ الربط والتحقق الحي عند تسليم الباكند.

## حزمة المصادقة القديمة

Tam-Authentication-v1.postman_collection.json ما زال عقد Auth الأصلي فقط؛
لم يُغير ضمن التجميع. يشمل ست عمليات، لا endpoint ضيف. نسخة ZIP القديمة
مؤرشفة لتسليم المصادقة السابق ولا تمثل عقد التطبيق الكامل.

أضيفت خرائط الاستضافة الخاصة في maps-v1: العكس ومعاينة GeoJSON والبحث المشترك
وطلب بلاطة PNG. المثال الثنائي لا يخزن جسم صورة في JSON. لا خدمات عامة
أو token في طلب البلاطات؛ الخدمات الخاصة غير مجهزة بعد.
