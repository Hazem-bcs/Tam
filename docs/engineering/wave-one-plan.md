# تم — الخطة النهائية قبل تكليف خمسة وكلاء

التاريخ: 2026-11-07. المستخدم صاحب قرارات المنتج، والمحادثة الرئيسية مشرف
التنسيق والتكامل، وخمسة وكلاء يملكون خمس ميزات. لم تبدأ المهام ولم تُنشأ
فروعهم بهذه الخطة؛ تُملأ بطاقات التكليف عند الإرسال الفعلي.

## التقسيم المقترح للدفعة الأولى

| الوكيل | المهمة | ملكية كود الميزة واختباراتها | الفرع المقترح عند التكليف |
|---|---|---|---|
| A | W1-HOME: الرئيسية | `lib/features/home/**` و`test/features/home/**` | `codex/w1-home` |
| B | W1-RIDE: طلب الرحلة | `lib/features/ride_request/**` و`test/features/ride_request/**` | `codex/w1-ride-request` |
| C | W1-TRIPS: طلباتي | `lib/features/trips/**` و`test/features/trips/**` | `codex/w1-trips` |
| D | W1-NOTIFICATIONS: الإشعارات | `lib/features/notifications/**` و`test/features/notifications/**` | `codex/w1-notifications` |
| E | W1-SETTINGS: الإعدادات والحساب الأساسي | `lib/features/settings/**` و`test/features/settings/**` | `codex/w1-settings` |

المسارات أعلاه داخل `apps/customer/`. لكل مالك أيضًا `docs/api/<feature>/**`
وتقريراته وصوره داخل مجلد تسليم مستقل يحدد في البطاقة. بادئة الفروع تتبع
إعداد المستودع الحالي ولا تفرض أداة أو مزوّدًا على الكاتب.

هذا تقسيم للنقاش النهائي قبل إرسال التكليفات. نفترض في هذه الدفعة أن
«طلباتي» تعني رحلات العميل، لا طلبات متجر أو مطعم؛ يُثبت هذا في مواصفات
التكليف. لا نضيف مجالات الطعام/التجارة أو صفحات السائق ضمنيًا.

## نطاق كل مالك وحدود التكامل

### A — Home

يبني تركيب الرئيسية وأقسامها وعرض الحالة والمدخل إلى طلب رحلة وروابط
طلباتي والإشعارات والإعدادات، بحسب مرجع العميل المعتمد. يملك بيانات
الرئيسية وعقدها إن احتاجت الخادم، ولا ينسخ قائمة الرحلات أو عداد الإشعارات
أو بحث الوجهة. يصل إلى الميزات عبر callbacks/واجهات يثبتها المشرف.

### B — طلب الرحلة

يملك اختيار الانطلاق والوجهة والبحث بمحاكاة، ثم اختيار الفئة وعرض عرض
السعر ومراجعة الطلب وتأكيد محلي محاكى. يعيد استخدام `GeoPoint` و`RideDraftBloc`
الحاليين ويطورهما ضمن نطاقه؛ لا ينقل نوعًا مشتركًا إلى core دون تنسيق.
يطلب المشرف منه واجهة عرض صغيرة ثابتة لبقية الميزات بدل استيراد تفاصيله.
عند انتقال المستخدم من رحلة سابقة يعاد إعداد الطلب، ولا يعاد استخدام السعر
القديم أو اعتبار الحجز السابق تأكيدًا جديدًا.

الخرائط وGPS والبحث الحي ومطابقة سائق حي والدفع الفعلي والتتبع والدردشة
ليست من متطلبات هذه الدفعة دون عقد/تكليف إضافي. مساحة خريطة محاكاة إن
استُخدمت تكون معلومة السلوك ولا تدّعي موقع الجهاز أو طرقًا حقيقية.

### C — طلباتي

يملك قائمة رحلات العميل وفلاترها وتفاصيلها وحالات التحميل والفراغ والخطأ،
مع ترقيم البيانات ومحاكاة الحالات ذات الصلة. حالات الإلغاء المسموح بها
وقواعده تثبت في عقده مع قواعد الرحلة. «اطلب مجددًا» يخرج طلبًا typed
لإعادة تعبئة الانطلاق والوجهة عبر نقطة التكامل، ولا يبني صفحة حجز ثانية.

### D — الإشعارات

يملك صندوق الإشعارات داخل التطبيق: القائمة والتفاصيل إن لزم، غير المقروء،
التعليم كمقروء، والوجهات المسموح فتحها. يملك عداد غير المقروء كعقد يستهلكه
تركيب التطبيق، ولا يفرض ملكية Home. تُثبت مع C/B قواعد وجهات الرحلات.
Push/FCM وتسجيل توكن الجهاز والتسليم بالخلفية مهمة لاحقة، ولا توحي المحاكاة
بأن إشعارًا جاء من خادم أو من نظام التشغيل.

### E — الإعدادات والحساب الأساسي

يملك صفحة الإعدادات وخياراتها وملفًا شخصيًا محاكى إن نص عليه التكليف.
يفصل الخيارات المحلية مثل اللغة عن بيانات الحساب الخادمية. لا يغير
`AuthUser` أو `AuthCubit` ولا يختلق هوية موثقة؛ هاتف الدخول الحالي مصدره Auth.
تغيير اللغة والخروج يتمان عبر واجهات التطبيق المتفق عليها، لا عبر بناء
`MaterialApp` أو ثيم أو جلسة موازية. الوضع الداكن يحتاج ثيمًا مركزيًا منفصلًا
وليس switch يعمل ظاهريًا فقط. العناوين المحفوظة والحذف النهائي للحساب
ومحفظة المال خارج هذه البطاقة ما لم يُحدّد نطاقها صراحة قبل التكليف.

## مرحلة المشرف قبل فتح التنفيذ — W1-BASE

1. ينشر الخطة والتعليمات في GitHub، ويتأكد أن Git نظيف وأن SHA المحلي
   والمرفوع متطابقان. كوميت الخطة ليس ادعاء اكتمال تجهيز runtime.
2. يجهز حزمة الصور ذات الصلة لكل ميزة بأسماء الملفات والحالات. يعتمد
   الشكل المطلوب، ويعلّم الفراغات التصميمية كمقترحات تحتاج حسمًا قبل بنائها.
3. يثبت العقود المشتركة القصيرة: الانطلاق/الوجهة ومدخل الحجز ومرجع الرحلة
   ووجهة الإشعار والعداد. المعرفات opaque strings، ولا تكشف الواجهة DTO/JSON.
   المال بوحدات صحيحة مع currency ودقة متفق عليها، والزمن ISO-8601 مع timezone؛
   يثبت cursor pagination والترتيب وحالات الرحلة والإلغاء وعدم تكرار التأكيد.
   يحدد مصدر حالة الرحلات المحاكاة وحقنه بين B وC: تأكيد رحلة يظهر في
   طلباتي، والإلغاء ينعكس على تفاصيلها، دون قائمتين مستقلتين تدعيان تمثيل
   البيانات نفسها. ينسق D وجهات الإشعارات مع معرفات موارد موجودة في السيناريو.
4. يجهز الوضع المركزي وفق [سياسة mock/API](mock-api-policy.md)، وحدود
   حقن المستودعات، وواجهات التنقّل والوصول للمحاكاة مع حماية api mode.
   يفوض تغييرًا مركزيًا محددًا لكاتب واحد عند الحاجة؛ لا يكتب الخمسة الملف نفسه.
5. ينسق مفاتيح الترجمة ومسارات التوجيه والاعتماديات الأولية. عند الحاجة
   المتأخرة لمفتاح أو route، يطلبها المالك ويصدر المشرف تغييرًا مركزيًا
   معلومًا بدل وضع نص/مسار hardcoded. مراجعة هذا التغيير جزء من التكامل.
6. يحفظ أساس التنفيذ المتحقق منه ويرفعه، ويسجل **SHA واحدًا كاملًا** في
   بطاقات الخمسة، مع أسماء الفروع وworktrees والملكية والقبول والمراجع.
   عندها فقط تتحول الميزات إلى READY ويمكن تكليفها.

لا يُعد غياب الباكند مانعًا لهذه الدفعة بعد تجهيز العقود والمحاكاة؛ غياب
قرار المنتج أو حد التكامل يظل مانعًا للجزء المعتمد عليه. لا نخترع قرارًا
نهائيًا داخل فرع ميزة ثم نفرضه على البقية.

## ما يسلمه كل وكيل

- تنفيذ الميزة داخل ملكيته، بواجهات مرتبة وملفات يفضل ألا تتجاوز 300 سطر.
- Domain repository وتطبيق Mock معزول وfixtures مطابقة للعقد؛ حالات
  النجاح والتحميل والفراغ والفشل وإعادة المحاولة والتعديلات ذات الصلة.
- عقد API عربي قابل للفهم وCollection Postman وأمثلة وREADME حسب
  [قائمة التسليم](api-handoff-template.md). إن كانت العملية محلية يذكر ذلك
  بدل إضافة API مصطنع. عقود الميزات الأولية تُراجع مبكرًا قبل اكتمال UI.
- اختبارات ذات معنى، ونتائج format/analyze/test الفعلية، وصور واجهة
  للغتين والهاتف والتابلت والخط الكبير والكيبورد بحسب الميزة.
- كوميت/كوميتات واضحة ثم SHA نهائي، وتقرير بالقيود والملفات المشتركة المطلوبة.
  لا يكفي إرسال «انتهيت» أو صورة دون تاريخ كود يمكن مراجعته.

إذا سمح التكليف برفع فرعه، يرفع الوكيل فرعه فقط باستخدام `[skip ci]`،
ثم يرسل الاسم وSHA للمشرف عبر المستخدم/قناة مأذون بها. خلاف ذلك يسلم
الكوميت محليًا أو patch معلوم الأساس. لا push إلى main ولا Actions تلقائيًا.

## المراجعة والتجميع

لا نحجز خمسة مراجعين دائمين. عند جاهزية تسليم، يسند المشرف مراجعًا مستقلًا
له؛ يمكن لمالك آخر متاح تبديل دوره مؤقتًا، لكن لا يراجع عمله بنفسه. ينشئ
المراجع فرعًا/checkout مستقلًا من SHA المطوّر، ويختبر الكود والعقد والصور
ويصحح أو يعيد ملاحظات. ارتباط الاعتماد بـSHA النهائي، لا اسم الفرع.

يبقى لكل ميزة مالكها حتى بعد المراجعة؛ لا ينتهي دوره إلا بعد إصلاح العيوب
والتكامل. إذا لم يتوفر مراجع، تبقى REVIEW ولا تُعتمد بتوقيع المطوّر وحده.
يجمع المشرف الفروع المعتمدة تدريجيًا في فرع تكامل، ويختبر العبور بين الميزات
وحراسة المسارات والتجاوب واتساق الحجز/طلباتي ووجهات الإشعارات في المحاكاة.
أي إصلاح تعارض يؤثر في السلوك يحتاج مراجعة متأثرة.
الدمج النهائي إلى main وتشغيل CI لهما تفويض مستقل حسب تعليمات المستخدم.

## إضافة ثلاثة وكلاء لاحقًا

يفحص المشرف اللوحة والملكية والتبعيات: يمكن إسناد مراجعات أو QA أو مهام
مستقلة مثل العناوين أو Push بعد تجهيز عقودها. لا يفتح فرعًا جديدًا داخل
ملفات يكتبها مالك آخر؛ العدد المتاح لا يحول المهمة المحجوبة إلى جاهزة.
