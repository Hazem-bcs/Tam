# تم — تطوير الميزات ببيانات Mock ثم ربط API

قرار المستخدم بتاريخ 2026-11-07: الباكند غير جاهز، ويُسمح ببناء الميزات
الجديدة بمحاكاة بيانات وسلوك قابلة للاستبدال. يحل هذا الإذن محل المنع
السابق لبيانات التشغيل الوهمية ضمن هذا النطاق. لا يغيّر عقد Auth أو الدخول
المؤقت دون OTP. سياسة المحاكاة واختيارها المركزي موجودة في أساس الدفعة؛ تطبيقات مستودعات الميزات وHTTP تُنفذ وفق بطاقاتها، ولا يوجد ربط حي بعد.

## حدود التصميم

نستخدم Repository Pattern مع حقن الاعتماديات الموجود؛ ليست هناك حاجة
لإضافة مكتبة أو إطار تصميم آخر. التسلسل هو:

```text
Page -> Cubit/Bloc -> Domain Repository
                         ^
                 Mock implementation OR API implementation
                         ^
                 اختيار مركزي عند تركيب الاعتماديات
```

- العقد والنماذج والفشل في `domain/`؛ لا تعرف Flutter أو JSON أو وضع التشغيل.
- المحاكاة في `features/<feature>/data/mock/`، وبها السيناريوهات والـfixtures
  فقط؛ لا تُزرع قوائم ثابتة في Pages أو Cubit ولا توضع مفاتيح mock في النماذج.
- تحويل JSON إلى domain في data، وتشارك المحاكاة والاتصال الحقيقي التحويلات
  والقواعد ذات المعنى. تتطابق fixtures مع أمثلة عقد API، ولا نكرر مصدر الحقيقة.
- وظائف القراءة والتعديل تحترم العقد نفسه في الوضعين، بما فيه الترقيم
  والفلاتر والحالات والفشل. الذاكرة المؤقتة للمحاكاة لا تصبح جلسة Auth حقيقية.
- لا نجمع مستودعات الميزات في generic repository أو utils ضخمة؛ مشاركة
  نماذج البيانات أو القواعد تكون بحدود متفق عليها ومالك واحد.
- السلوك العابر للميزات يحتاج مصدر حالة محاكاة واحدًا بحدود متفق عليها:
  إنشاء/إلغاء رحلة ينعكس على طلباتي، ومعرّفات وجهات الإشعارات متوافقة مع
  السيناريو. لا يُنشئ كل وكيل قائمة موارد مستقلة ثم يتوقع اتساقها تلقائيًا.

## اختيار الوضع المركزي

الإعداد `DATA_MODE=mock|api` داخل `AppConfig`، مع خيارات مستقلة
لكل ميزة عند الربط التدريجي: `HOME_DATA_MODE` و`RIDE_REQUEST_DATA_MODE`
و`TRIPS_DATA_MODE` و`NOTIFICATIONS_DATA_MODE` و`SETTINGS_DATA_MODE`
و`ADDRESSES_DATA_MODE` للعناوين المحفوظة.
متابعة الرحلة تستخدم `ACTIVE_TRIP_DATA_MODE`، وسيناريو محاكاتها المركزي
`ACTIVE_TRIP_MOCK_SCENARIO=success|no_driver|disconnect`. المحرك مملوك
للتطبيق ويحدث Trip نفسه حتى عند مغادرة الصفحة؛ لا تنفيذ خلفي بعد إغلاقه.
يرث خيار الميزة الوضع العام إذا لم يحدد؛ القيم غير المعروفة خطأ إعداد واضح.
الخيارات منفذة عبر AppConfig وFeatureDataModes، وتُحقن قيمتها في نقاط دخول الميزات المسجلة؛ لا يختارها Widget أو Cubit.

أثناء المرحلة الحالية يكون mock هو الوضع الافتراضي للميزات الجديدة فقط.
تقرأ نقطة تركيب الاعتماديات الإعدادات مرة واحدة وتحقن التنفيذ المناسب؛
لا يقرأ كل Widget متغير بيئة ولا يضع شرط `if mock` داخل تدفق المستخدم.
يُوثق الوضع في README التشغيل والتسليم، مع مؤشر مركزي هادئ للمحاكاة عند
عرض عمليات قد تُفهم كحجز حقيقي. لا نكرر شارات تجريبية داخل كل قسم.

إذا لم يجهز API implementation، يعرض اختيار api عدم توفر التكامل بوضوح؛
لا يسقط إلى mock تلقائيًا، ولا يسجل الطلب كأنه وصل للخادم.
لا يكتب الوكيل اتصالًا بطرف غير موجود أو يعلن اختباره حيًا.

## السيناريوهات والتحقق

- fixtures غير شخصية، مستقرة المعرّفات، بلا أسرار أو حسابات حقيقية.
- دعم نجاح/تحميل/فراغ/فشل/إعادة محاولة، وحالات التعديل المناسبة لكل ميزة.
  اختيار السيناريو مركزي وقابل للحقن للاختبار، لا يعتمد على العشوائية أو
  أرقام هواتف سحرية. استخدم ساعة قابلة للحقن إن كان الزمن جزءًا من السلوك.
- لا تضف تأخيرات طويلة عشوائية لإظهار spinner؛ اختبر التأخير والتحكم في
  الطلبات بشكل حتمي. أي إعادة ضبط لبيانات المحاكاة تكون موثقة.
- بيانات المحاكاة ليست بديلًا عن اختبارات parsing والعقد والأخطاء. عند
  إضافة HTTP لاحقًا اختبر الطلب والاستجابة عبر transport بديل قبل الاختبار الحي.
- أي حجز أو سعر أو قراءة إشعار أو تعديل حساب الآن محاكاة محلية، وليست أثرًا
  على خادم. السعر الحقيقي والتوفر وتأكيد الرحلة صلاحية الباكند لاحقًا.

## Auth والوصول للبيانات

يبقى `TEMPORARY_PHONE_ENTRY` افتراضيًا كما هو؛ `localAccess` وguest لا يصبحان
`authenticated`. لا ننشئ access/refresh tokens أو مستخدمًا موثقًا لتشغيل mocks.
يقرر المشرف الوصول لشاشات المحاكاة مركزيًا عند تجهيز المسارات. في api mode،
البيانات الشخصية وعمليات الحجز المحمية تتطلب الجلسة الحقيقية وفق العقد،
حتى لو أمكن تصفح الواجهة نفسها بمحاكاة سابقًا. لا تُضعف حراسة API من أجل العرض.
المحاكاة لا تطلب مفاتيح خرائط أو SMS أو أذونات نظام حقيقية لتختلق نجاحًا؛
أي محاكاة موقع أو خريطة توثق بصفتها محاكاة ولا تزعم أنها موضع الجهاز.

## عندما يجهز الباكند

1. يعلن المستخدم جاهزيته ويوفر العنوان والتهيئة اللازمة، ويقارن المشرف
   العقود المتفق عليها بما نُفذ؛ الاختلافات تُحل صراحة قبل تغيير الوضع.
2. ينفذ مالك الميزة API repository والـDTO/mapping بحسب الحاجة، ويسجل
   التطبيق الحقيقي في DI؛ يضيف التخزين الآمن للمصادقة ضمن مهمة Auth منفصلة.
3. يُختبر النجاح والفشل والجلسات والانقطاع والترقيم ومنع تكرار الحجز؛
   ثم تُنقل الميزة وحدها إلى api دون تغيير Pages أو Cubit بسبب مصدر البيانات.
4. بعد استقرار الربط، يمكن حذف `data/mock/` وتسجيله وخياراته غير اللازمة،
   ونقل fixtures المفيدة إلى `test/fixtures` وتحديث الاختبارات والوثائق.
   لا نحذف اختبارات العقد ولا ننسخ بيانات التشغيل الوهمية داخل الواجهة.

تغيير الخيار وحده لا يُنشئ ربط HTTP. تعطيل mock لا يضمن وحده حذف ملفاته
من المستودع أو تقليل حجم المصدر؛ الحذف المنظم خطوة مستقلة بعد التحقق.
