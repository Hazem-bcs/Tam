# تم — متطلبات حزمة التسليم لمطور الباكند

لكل ميزة تعتمد على الخادم مجلد مستقل:

```text
docs/api/<feature>/
  README.ar.md
  <feature>-v1.md
  <feature>-v1.postman_collection.json
  examples/
```

هذه الملفات يسلّمها مالك الميزة مع الكود، وليست ملفات موجودة مسبقًا لكل
ميزة الآن. يضيف OpenAPI إذا كانت هناك حاجة متفق عليها، وليس مصدرًا رابعًا
يدويًا يناقض العقد والأمثلة. الحزمة قابلة للإرسال كمجلد أو ZIP عند التسليم.

## محتوى README والعقد

- اسم الميزة وإصدار العقد وحالته: مقترح/معتمد مع الباكند/منفّذ/متحقق حيًا.
  عقود المرحلة الحالية **طلبات تنفيذ للباكند** وليست وصفًا لخادم موجود.
- شرح عربي لتدفقات المستخدم وما يحتاجه كل تدفق من الخادم، وما يبقى محليًا.
- عنوان أساس متغير ومسارات نسبية وmethods وheaders وauth لكل عملية.
- أسماء الحقول وأنواعها، required/nullable، القيم المسموحة والافتراضات،
  الوحدات والقيود والتواريخ والمناطق الزمنية والترتيب والترقيم والفلاتر.
- جميع حالات النجاح والأخطاء المطلوبة وHTTP statuses وأكواد خطأ ثابتة
  وقواعد التحقق، بما فيها انقطاع الجلسة والمنع والتعارض وإعادة المحاولة.
- سلوك التعديل وتكراره، خاصة idempotency لتأكيد الحجز وما يحدث عند إعادة
  المحاولة بعد timeout. لا تكفي عبارة «نعيد الطلب» دون اتفاق مع الخادم.
- النقاط المفتوحة والافتراضات ومسؤوليات الطرفين ومصفوفة ربط كل شاشة/فعل
  بعملية Repository وendpoint؛ لا تُخترع endpoints لإعداد محلي فقط.

التزم بالقواعد العامة الحالية في [عقد Auth](../api/authentication-v1.md):
`data` للنجاح و`error.code` و`error.message.ar/en` للفشل، والنصوص متعددة
اللغات حين يلزم. لا تغيّر عقد Auth نفسه ولا تنشئ شكل أخطاء منافسًا لكل ميزة.
يُثبت المشرف قواعد الترقيم والمعرّفات والمال والتواريخ المشتركة قبل التوزيع؛
الأمثلة الأولية لا تُعد اتفاقًا نهائيًا على هذه التفاصيل.

## ملف Postman المطلوب

- Collection قابلة للاستيراد (v2.1)؛ وصفها يشرح للباكند الهدف وتسلسل الاستخدام.
- متغيرات مثل `base_url` و`access_token` ومعرّفات الموارد، دون أي أسرار حية.
- أمثلة طلبات واقعية اصطناعية لكل عملية، وsaved responses للنجاح والأخطاء
  المهمة، بما فيها التحقق والترقيم والفراغ والمنع وفق نطاق الميزة.
- المعرفات والحقول والـfixtures متطابقة مع العقد ومع parsing Flutter؛
  روابط الصور والأرقام الاصطناعية ليست موارد إنتاج ولا بيانات شخصية.
- README يشرح الاستيراد، المتغيرات وتسلسل الطلبات. لا يحتاج المطور قراءة
  كود Flutter لمعرفة المطلوب منه. لا تُرفع الحزمة إلى خدمة عامة تلقائيًا.

## تحقق التسليم

1. فحص JSON وبنية Collection واستيرادها فعليًا إن توفرت أداة لذلك؛ يذكر
   الوكيل ما فحصه فعلًا، ولا يساوي JSON صالحًا باستيراد أو طلب حي ناجح.
2. اختبار أن أمثلة النجاح والأخطاء تُقرأ إلى نماذج الميزة الصحيحة، وأن
   المحاكاة تلتزم بالترقيم والقيود والحالات الموثقة.
3. مراجعة مستقلة للكود والعقد والأمثلة معًا؛ لا يُعتمد تغيير حقل في طرف واحد.
4. يراجع المشرف التناسق بين الميزات ويجهز حزمة الباكند النهائية؛ تظل العقود
   بإصدارات معلومة، وأي تغيير بعد اعتمادها يُنسق مع Flutter والباكند معًا.
