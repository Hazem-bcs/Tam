# تم — قوالب تكليف وتسليم لأي وكيل

هذه القوالب مستقلة عن المزوّد والواجهة. تصلح لوكيل برمجة محلي أو على جهاز آخر، أو لمحادثة نصية عند إرفاق السياق اللازم. ملفات المشروع والكوميتات هي المرجع؛ لا نفترض أن وكيلًا يستطيع الاطلاع على محادثة وكيل آخر.

لإدخال وكيل جديد استخدم [ملف الاستقبال](agent-onboarding.md)، ثم سلّمه
بطاقة مكتملة. اختر مراجع الصورة من [الفهرس البصري](design-reference-index.md)
وسجل مساراتها وأجزاءها المطلوبة في البطاقة بدل الإشارة للمجلد كله.

## بداية كل تكليف

يضع المشرف التعليمات الافتتاحية التالية مع بطاقة المهمة، سواء كان الوكيل من Codex أو Claude أو Gemini أو غيرها:

```text
أنت تعمل على مشروع Tam | تم.
اقرأ AGENTS.md من جذر المستودع، ثم docs/engineering/parallel-work.md
والوثائق ذات الصلة ببطاقة المهمة. استخدمها مصدرًا موحدًا للشروط.
إذا لم تكن الملفات أو صور التصميم متاحة لك، صرّح بذلك قبل أي عمل يعتمد عليها.
لا تفترض الاطلاع على محادثات الفريق أو التحميل التلقائي لتعليمات المستودع.

اعمل بالدور والنطاق المرسلين فقط. لا تغيّر الثيم أو الإعدادات أو العقود
المشتركة أو سلوك Auth خارج الملكية الممنوحة. لا ترفع أو تدمج إلى main
أو تشغّل CI خارج تفويض المهمة. لا تدّعِ تنفيذ اختبار أو فحص بصري لم تنفذه.

ابدأ بتأكيد: معرّف المهمة، دورك، SHA الفعلي/النسخة التي أمامك، الملفات
المملوكة، المراجع التي قرأتها، والأدوات أو المدخلات غير المتاحة.
ثم نفّذ المهمة وقدّم التسليم بالنموذج المحدد أدناه.
```

إذا كانت الواجهة لا تقرأ المستودع، يرفق المشرف محتوى التعليمات والملفات اللازمة والصور أو diff مربوطًا بنسخة معلومة؛ إرسال أسماء الملفات وحدها لا يوفر سياقًا يمكن العمل عليه.

## بطاقة المهمة التي يملؤها المشرف

```text
Task ID / Title:
Role: SUPERVISOR | DEVELOPER | REVIEWER | QA
Feature owner / reviewer identifier (reviewer may be assigned at submission):
Repository location or supplied snapshot:
Baseline SHA / dependency SHAs:
Implementation branch / review branch / worktree:
Current reviewed/input SHA:

Goal and observable acceptance criteria:
Included scope:
Excluded scope:
Owned paths:
Shared-file owner and change-request route:
Design references supplied and required visual states:
Agreed interfaces / route access / localization keys:
Data mode / mock scenarios / repository contract:
API contract / Postman / examples / backend handoff paths:
Dependencies and READY conditions:
Required verification and actual available execution environment:
Deliverables / limitations / communication method authorized by the user:
```

معرّف الوكيل يصف دوره ولا يفرض مزوّدًا أو نموذجًا. تظل ملفات الترجمة والثيم وDI والمسارات والاعتماديات تحت تنسيق المشرف وفق بروتوكول العمل المتوازي.

## إضافة لدور المشرف

```text
ثبّت نقطة البداية والعقود والملكية، ثم أنشئ بطاقات صغيرة ذات نتائج واضحة.
أبقِ لوحة المهام مرجعًا واحدًا، وحدد من يستطيع تنفيذ كل مهمة ومراجعتها.
لا توزع مهمة قبل جاهزية مدخلاتها، ولا تمنح ملفًا مشتركًا لكاتبين بالتزامن.
مرّر السياق والمخرجات بين المزوّدين؛ لا تشترط أدوات تواصل خاصة بمنصة معينة.
اجمع فقط الرؤوس المعتمدة على SHAs محددة، واختبر النسخة المجمعة.
حل التعارضات الذي يغير السلوك يحتاج مراجعة متأثرة جديدة.
اذكر ما اكتمل وما بقي وحدود التحقق، والتزم بوجهة الدمج والنشر المأذون بها.
```

## إضافة لدور المطوّر

```text
نفّذ بطاقة المهمة ضمن الملفات المملوكة، باتباع AGENTS.md ونظام التصميم.
استخدم الثيم والمكوّنات والإعدادات العامة، وحافظ على حدود الطبقات والعقود.
اختبر السلوك والحالات الاستثنائية والتجاوب واللغتين حسب المهمة.
افصل Mock في data/mock خلف عقد Repository؛ لا تضع بيانات ثابتة أو شروط
وضع التشغيل داخل UI/Cubit. سلّم عقد API وPostman والأمثلة وفق سياسة المشروع.
اطلب أي تغيير مشترك من مالكه؛ لا تتجاوزه بنسخة مكررة أو قيمة hardcoded.
سلّم كوميتات واضحة وSHA نهائيًا، أو patch مرتبطًا بالنسخة المرسلة إذا لم
يتوفر Git. اذكر الفحوص المنفذة والتي تعذر تنفيذها بدقة.
جمّد النسخة المسلمة أثناء المراجعة إلى أن تستلم طلب متابعة من المشرف.
```

## إضافة لدور المراجع

```text
راجع النسخة المحددة بالـSHA، وليس ملخص المطوّر وحده.
اقرأ الشروط والعقد والتغيير كاملًا والملفات المحيطة المؤثرة.
تحقق من صحة السلوك، Clean Architecture وSOLID وDRY، الثيم والإعدادات،
التجاوب، RTL/LTR، إدارة الموارد، التوجيه والاختبارات بحسب نطاق المهمة.
راجع عزل المحاكاة وتطابقها مع العقد وPostman، ومنع fallback من API إلى
Mock، والحفاظ على Auth وحماية البيانات الحقيقية عند تغيير وضع التشغيل.
شغّل التحقق بنفسك إذا كانت الأدوات متاحة، وافحص الصور المرسومة للواجهة.
صحح الأخطاء ضمن فرع المراجعة وملكيتك المسموحة، أو أعطِ طلب إصلاح محددًا.
لا تحذف الاختبارات لتخفي الفشل ولا تعتمد تعديل عقد أو نطاق غير مأذون به.
اربط الاعتماد بالـSHA النهائي بعد التصحيحات واذكر المخاطر والقيود الباقية.
إذا كانت المراجعة نصية فقط، أعلن REVIEW_ONLY وحدودها؛ لا تدّعِ اعتماد
تنفيذ لم تره أو اختبارات لم تشغلها.
```

## إضافة لدور QA

```text
افحص SHA مرشح التكامل الذي سجله المشرف، دون تغيير مستقل في نطاق الميزات.
اختبر رحلة المستخدم كاملة، وسلوك الرجوع والدخول المؤقت والضيف والصلاحيات،
والهاتف والتابلت واللغة والخط الكبير ولوحة المفاتيح حسب معايير التسليم.
سجل خطوات إعادة إنتاج كل مشكلة والنتيجة المتوقعة والفعلية والأدلة.
نسق استخدام المحاكي مع المشرف، ولا تشغّل نسخة فرع مختلف عليه بالتزامن.
```

## تسليم موحد يمكن نقله بين أي مزوّدين

```text
Task ID / Role:
Input/baseline SHA:
Implementation SHA or supplied patch identity:
Final SHA after fixes (if available):
Branch / worktree / snapshot location:
Changed files and user-visible result:
Active data mode / API contract version / Postman and fixture paths:
Acceptance criteria met / not met:
Tests: exact command, environment, result, failure or NOT_RUN reason:
Visual review: actual image paths, environment, sizes/locales inspected:
Findings: severity, file/line, reproduction and fix:
Shared changes requested / unresolved blockers / limitations:
Verdict: READY_FOR_REVIEW | CHANGES_REQUIRED | REVIEW_ONLY | APPROVED_AT_SHA
Exact approved SHA and verification evidence (when applicable):
```

يُعاد تقييم الاعتماد إذا تغير الكوميت. عند استيراد patch من وكيل بلا وصول إلى Git، يسجل المشرف SHA الناتج ويعرضه للمراجع بعد الاستيراد؛ هوية الـpatch وحدها ليست اعتمادًا تلقائيًا للكوميت.

## قيود القدرة والوصول

- اكتشاف `AGENTS.md` أو `CLAUDE.md` أو `GEMINI.md` يختلف حسب العميل؛ لذلك تُرسل التعليمات الافتتاحية صراحة في كل تكليف.
- القيد العددي لأداة تعاون في جلسة أو مزوّد لا يصبح قاعدة للفريق كله. يحدد المشرف التزامن حسب الأدوات والمهام المستقلة والموارد الفعلية.
- الوكيل الذي لا يستطيع تشغيل Flutter أو فحص الصور يصرّح بذلك؛ يوفر المشرف جهة تحقق قادرة بدل قبول نتيجة مفترضة.
- التعليمات والمواصفات والنسخ المشتركة تُنقل كملفات/صور/كوميتات أو patches، دون اشتراط ذاكرة مشتركة أو آلية dispatch خاصة بمزوّد.
