# تم — مراحل تطوير تطبيق العميل

قرار المستخدم: 2026-11-08. ينطبق على جميع الملاك والمراجعين والمشرف،
بصرف النظر عن مزوّد الوكيل. يحدّث هذا القرار معيار القبول البصري السابق؛
لا ننتظر التحسين البصري النهائي لدمج ميزة سليمة في المرحلة الأولى.

## المرحلة الأولى — بنية التطبيق وتدفقاته وعقود الباكند

- نثبت مسؤولية كل feature، ونماذج Domain وقواعدها وعقود repositories،
  وطبقة Data والتحويلات والمحاكاة المعزولة، وPresentation اللازمة لتجربة
  التدفق كاملًا. نضيف طبقات/use cases عند وجود حاجة حقيقية فقط.
- نستخدم واجهة مبدئية قريبة من الهدف والصور كي نعرف المدخلات والعمليات
  والحالات المطلوبة. لا نعتمد شاشة شكلية تخفي نقص السلوك أو البيانات.
- نكمل النجاح والتحميل والفراغ والخطأ وإعادة المحاولة، والتنقل والإلغاء
  ومنع تكرار العمليات وعزل بيانات الجلسات وتناسق الحالة بين الميزات.
- نسلّم لكل feature تعتمد على الخادم عقد API بإصدار، وREADME عربيًا،
  وPostman وأمثلة متوافقة مع mock/parsing. العقود مقترحة حتى يتفق معها
  الباكند؛ الربط الحي يبدأ عند إعلان المستخدم جاهزيته وتوفير تهيئته.
- نلتزم من البداية بالثيم والتوكنز والمكونات المركزية وRTL/LTR والتجاوب
  والخط الكبير والكيبورد وإمكانية الوصول، وبنظافة الكود والملفات المركزة.
  لا نقبل overflow أو عناصر غير قابلة للاستخدام باعتبارها «تجميلًا مؤجلًا».
- يراجع وكيل مستقل SHA معينًا؛ تُحل عيوب السلوك والعقود والتكامل ثم يدمج
  المشرف النسخة ضمن فرع التكامل ويختبر الرحلة العابرة للميزات.
- تُسجل فروق الصور والأصول والمسافات والخطوط والتفاصيل البصرية كمهمات
  للمرحلة الثانية، ولا تكون وحدها مانع دمج أو ادعاء اعتماد بصري نهائي.

اكتمال الدفعة الأولى بخمس ميزات لا يعني اكتمال المرحلة الأولى لكل التطبيق؛
تليها الميزات المتفق عليها مثل العناوين والجدولة والرحلة الجارية والمحادثة
وحالات الإنهاء والتقييم والدعم بحسب بطاقات وعقود يثبتها المشرف.

## المرحلة الثانية — تحسين التصميم صفحةً صفحة

تبدأ بعد اكتمال تدفقات التطبيق المتفق عليها في المرحلة الأولى. نعود إلى
كل صفحة وحالاتها، ونقارن بالمراجع، ونحسن البنية البصرية والصور والأيقونات
والخطوط والكثافة والمسافات والحركات والتناسق على الهاتف والتابلت.

تظل الأعمال البصرية داخل نظام تصميم واحد، مع صور فعلية قبل/بعد ومراجعة
على المقاسات واللغتين والخط الكبير. نحافظ على Domain/Data والعقود والسلوك
المختبر؛ إذا كشف تحسين التصميم عملية أو معلومة جديدة، ننسق تغيير العقد
والسلوك صراحةً بدل اختراع endpoint أو نقل قواعد العمل إلى widgets.

## ما لا يتغير

Auth والضيف وlocalAccess والتجاوز المؤقت لـOTP كما هي. المحاكاة ليست
حجزًا أو دفعًا حقيقيًا، وAPI لا يسقط بصمت إلى mock. فحوص format/analyze/test
وإدارة الموارد وملكية الملفات وSHA التسليم تبقى إلزامية بحسب AGENTS.md.
لا يعني دمج المرحلة الأولى تفويض main أو تشغيل Actions أو جاهزية النشر.

## تثبيت نطاق تسليم الباكند — 2026-11-09

أكد المستخدم أن التسلسل هو: استكمال منطق تطبيق العميل بالمحاكاة وعقوده،
ثم تسليم Collection واحدة شاملة في Postman، ثم تحسين الواجهات والأنميشن
والألوان أثناء تنفيذ الباكند، ثم الربط الحقيقي عند جاهزيته. تنفيذ HTTP
والخدمات الحية ليس شرطًا لبدء التحسين البصري بعد تسليم العقد.

النطاق الإضافي المعتمد: حذف الحساب، تغيير رقم الهاتف، الاتصال بالسائق.
المحفظة والدفع الإلكتروني والكوبونات مؤجلة صراحة. لا تغيير لتجاوز OTP
المؤقت عند الدخول؛ تحقق العمليات الحساسة مستقل ولا يصنع جلسة باكند.
