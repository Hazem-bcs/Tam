## النطاق المعتمد

المستخدم اختار الرحلات الحالية + حذف الحساب وتغيير الرقم والاتصال بالسائق،
وتأجيل المحفظة والدفع الإلكتروني والكوبونات. المطلوب محاكاة متماسكة
وعقود Domain/Data وتجربة قابلة للاختبار ثم ملف Postman موحد، قبل الصقل البصري.

## الملكية والعقود

features/account_management وdriver_contact واختباراتهما وحزم API والتسليم،
والربط المشترك في app/config/router/DI/الجلسة/Settings/ActiveTrip وARB،
وسكربت تجميع Postman واختباراته. لا تعديل Auth API أو تجاوز الدخول المؤقت.
لا SDK في Domain، ولا fixtures في UI، ولا API fallback، ولا push/main/Actions.

إدارة الحساب: أهلية من رقم الجلسة والمخزن المشترك؛ الضيف بلا حساب لا
ينفذ العمليات. تمنع رحلة غير منتهية تغيير الرقم والحذف في الطلب والتأكيد.
تغيير رقم سوري مع تحقق OTP للرقم الجديد؛ حذف بتأكيد صريح وOTP للرقم الحالي.
هذه اختيارات تنفيذ موثقة قابلة للتعديل في السياسة المركزية، وليست سياسة
احتفاظ قانونية أو دمج حسابات. نجاح أي منهما ينهي الجلسة المحلية؛ الخادم
مسؤول عن إبطال الجلسات وفق العقد. لا إنشاء مستخدم موثق من المحاكاة.

نية ومعرف ثابتان عند فقد الرد، منع التكرار، cooldown/expiry/attempts
بساعة محقونة، إبطال الرمز السابق بعد resend، حسم العملية قبل السماح
بنية مختلفة، وحماية الهوية/الجيل/الخروج من الردود المتأخرة. credential
استعادة عملية حساسة يبقى في data مستقبلًا، لا Cubit state أو logs.

الاتصال: من رحلة نشطة ذات سائق فقط، مصدر Trip نفسه؛ تحقق trip/driver
والصلاحية قبل فتح تطبيق الهاتف. رقم E164 فقط، لا URL arbitrary ولا
إذن اتصال مباشر. المحاكاة تستخدم dialer بديلًا ولا تتصل برقم fixtures.
فتح تطبيق الهاتف لا يثبت اتصالًا أو رد السائق. backend يحدد رقمًا مخولًا
قد يكون وسيطًا؛ لا تعهد ببنية إخفاء أرقام غير متوفرة.
